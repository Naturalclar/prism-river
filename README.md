# Prism River

ブラウザだけで完結するマルチトラック音声エディタ。音声ファイルをドロップして並べ、ミックスして書き出す。

**サーバーを持たない。** 読み込んだ音声は端末から出ない — アップロードもアカウントも無く、`index.html` を開けば動く。これはプライバシー上の要件であると同時に、このプロジェクトの問い（**サーバー無しの Web でどこまで DAW たりうるか**）そのものでもある。

名前は騒霊三姉妹から。ルナサが弦、メルランが管、リリカが鍵盤を受け持つ編成をそのまま構造に借りていて、トラックの先頭3色はこの3人に対応する。将来のグループバスも同じ3系統で切る予定（下記）。

ライセンスは **GPL-3.0**（[`LICENSE`](LICENSE)）。将来 `aubio` や `Rubber Band` など GPL の音楽資産を WASM で持ち込む可能性を残すための選択（[#19](https://github.com/Naturalclar/prism-river/issues/19)）。

公開先は **https://smashcat.dev/prism-river** 。[`Naturalclar/smashcat.dev`](https://github.com/Naturalclar/smashcat.dev) が Cloudflare Worker としてホスト名を持ち、`/prism-river/*` を GitHub Pages へプロキシしている（`/medley-generator` と同じ構成）。**実体は GitHub Pages のまま**で、`main` への push で更新される（`.github/workflows/ci.yml` の `deploy` ジョブ）。`naturalclar.github.io/prism-river/` でも同じものが開くが、**人に渡すのは smashcat.dev 側**。

SNS に貼ったときのカード（OGP）は `index.html` のメタタグと `public/ogp.png`。画像は `pnpm ogp` で生成する（`scripts/ogp/`。テンプレート HTML を Playwright で 1200×630 撮影するだけで、外部の画像素材は持ち込まない）。**`og:url` / `og:image` / canonical は絶対 URL でハードコード**してある——SNS のクローラは相対パスを辿らないため。公開先を変えるときはここも手で直す。

`vite.config.ts` の `base` を `'./'`（相対）にしてあるのは、この載せ替えのため。接頭辞を埋め込まない代わりに**末尾スラッシュが必須**で、Worker 側の `normalizeTrailingSlash` が `/prism-river` を `/prism-river/` に寄せている。base を絶対パスに変えるときは Worker の設定も対で変える。

## 使う

```
pnpm install
pnpm dev
```

開いたページに mp3 / wav / m4a / ogg / opus / flac / webm（音声）をドロップするだけ。1ファイル＝1トラック。音声つき動画（mp4 / mov / webm / mkv）をドロップすると音声トラックだけを取り込む。**MIDI（.mid）** は内蔵シンセでレンダーしてオーディオトラックにする。実際に読めるかはブラウザの `decodeAudioData` 次第（下の対応表）。

| 操作 | |
| --- | --- |
| 再生 / 一時停止 | `Space` またはトランスポート |
| シーク | ルーラーをクリック |
| ループ範囲 | ルーラーを横にドラッグ。端は他クリップの開始 / 終端や 0 秒にスナップ（`Shift` で無効）。帯の × で解除して全体ループへ戻す |
| クリップの移動 | 波形を横にドラッグ。他クリップの開始 / 終端や 0 秒に近づくとスナップ（`Shift` で無効） |
| クリップのトリム | 左右端をドラッグして頭尻を詰める。移動と同じく他クリップの開始 / 終端や 0 秒にスナップ（`Shift` で無効） |
| フェードイン / アウト | クリップ上端の丸ハンドルをドラッグ |
| エフェクト | ヘッダの `FX` → EQ 3バンドとコンプレッサー |
| テンポ / ピッチ | ヘッダの `TS` → テンポ 0.5〜2倍・ピッチ ±12半音。**互いに独立**（遅くしても音程は変わらない） |
| グループバス | ヘッダの 弦 / 管 / 鍵盤 で割り当て。バス音量は Deck の `Bus` |
| トラックの選択 / 削除 | クリップかヘッダをクリック → `Delete` |
| トラックの複製 | 選択して `Ctrl+D` / `Cmd+D`。音量・トリム・FX・バスごと複製される |
| 右クリックメニュー | クリップかヘッダを右クリック → 複製 / 削除 |
| プロジェクトのファイル書き出し / 読み込み | Deck の `プロジェクトを書き出す` → `.prism`（無圧縮 ZIP）。読み込みは `プロジェクトを読み込む`（音声と同じドロップ / ピッカーでも開ける） |
| 新規プロジェクト | Deck の `新規プロジェクト`。トラックを全部消してまっさらに戻す。**端末内の保存データも消える**ので確認してから |
| 音量 / パン / ソロ / ミュート | 左のトラックヘッダ |
| マイク録音 | トランスポートの ●。録音中は録れている範囲が破線のクリップで伸びる。もう一度押すと停止してトラックになる |
| MIDI キーボードで録る | トランスポートの ♪。弾いたノートを停止時に内蔵シンセでレンダーしてトラックにする（Web MIDI 対応ブラウザのみ） |
| ドラムを足す | Deck の `ドラムを追加` → 16ステップの格子。ヘッダの `D` で開き直す |
| 打ち込み | Deck の `打ち込みを追加` → ピアノロール。ヘッダの `R` で開き直す |
| 続きから始める | 何もしない。リロードすると前回の続きから開く（Deck の `自動保存` で切れる） |
| webm で書き出す | Opus で書き出し。実時間で録るのでミックスの長さぶんかかる |
| MP3 で書き出す | WASM（LAME）でオフラインエンコード。実時間はかからない |

## 今できること

- 複数ファイルの同時読み込みと `decodeAudioData` によるデコード
- 動画コンテナ（mp4 / mov / webm / mkv）からの音声取り込み。`decodeAudioData` にバイト列をそのまま渡して音声トラックだけを取り出す（依存ゼロ・対応はブラウザ依存、下記）
- Canvas のピーク波形描画（列ごとに min/max を畳む）
- 再生・停止・ループ、シーク、プレイヘッド追従
- ループする範囲の指定（#88）。ルーラーの横ドラッグで区間を決めると、その終わりで区間の頭へ折り返す。区間なしなら従来どおりミックス全体を繰り返す。端は移動・トリムと同じスナップ（8px・`Shift` で無効）でクリップの端に吸着し、区間は保存・復元にも載る。**書き出しは常にミックス全体**（区間だけの書き出しは別の話なので入れていない）
- トラックごとの音量（`GainNode`）・パン（`StereoPannerNode`）・ソロ・ミュート
- クリップの開始位置を横ドラッグで変更（再生中でも即座に組み直す）。他クリップの開始・終端と 0 秒へのスナップ付き — 自分の左端・右端の両方が候補で、しきい値は 8px（ズームインするほど精密）。吸着中は枠色が変わり、`Shift` ドラッグで無効化できる
- クリップの非破壊トリム（左右端をドラッグ。再生・書き出しの両方に効く）。移動と同じスナップが効く — ドラッグしている端がタイムライン上で他クリップの開始・終端や 0 秒に近づくと吸着し、しきい値・枠色・`Shift` での無効化まで移動と共通（#84）
- フェードイン / アウト（上端の丸ハンドル。`GainNode` の `linearRampToValueAtTime`）
- トラックごとの EQ 3バンド（`BiquadFilterNode` の低棚 200Hz / ピーキング 1kHz / 高棚 4kHz）とコンプ（`DynamicsCompressorNode`）。再生中はライブに効き、書き出しにも同じ設定が乗る
- グループバス3系統（弦=ルナサ / 管=メルラン / 鍵盤=リリカ）。トラックを `pan → busGain → master` でサブミックスにまとめ、バス音量が再生・書き出しの両方に効く。割り当てはトグルで、外すと Master 直結に戻る
- トラックのクリック選択と `Delete` キーでの削除、`Ctrl+D` / `Cmd+D` での複製（設定ごと写る。AudioBuffer と元ファイルは参照共有なので PCM メモリは増えない。ドラム / ロールのパターンはディープコピーで独立に編集できる）
- マイク録音（`getUserMedia` + `MediaRecorder`。停止すると録った音声がそのままトラックになり、**録り始めたタイムライン上の位置に置かれる**（再生に重ねて録れる）。録音中はレベルメーターに入力レベルが重なるので無音録りに気づける。録った音声も他のトラック同様、端末から出ない）
- 録音中のリアルタイム表示（#63）。停止してデコードが終わるまでトラックは現れないので、そのあいだ**録れている範囲を仮のクリップとして録り始めた位置から伸ばす**（破線の枠が「まだ確定していない」印）。**波形として正確なものではない** — 値は `AnalyserNode` をフレームごとに読んだピークで、フレーム間（約16ms）の瞬間的なピークは取りこぼす。狙いは「いま、どこに、鳴っている音が録れているか」が分かることで、正確な波形は停止後のデコードで出るものに丸ごと差し替わる
- MIDI キーボードからの録音（#56 段1）。`navigator.requestMIDIAccess` で note on/off を受け、停止すると読み込んだ MIDI と同じ内蔵シンセでレンダーしてトラックにする。録れるのは音声ではなくノート列なので容量はほぼゼロで、保存・復元はノート列の JSON から再レンダーする。録音中は受信した音数がログに出る（無音録りならぬ「無反応録り」に気づける）。**弾いている音をその場で聴くリアルタイム発音は未実装**（下の「これから」）
- マスター音量、`AnalyserNode` による L/R レベルメーター、ズーム
- `OfflineAudioContext` によるミックスの一括レンダーと WAV 書き出し
- webm（Opus）書き出し（`MediaStreamAudioDestinationNode` + `MediaRecorder`。一括レンダーと違い**実時間かかる**のが仕様で、WAV の数百倍速との対比もこの台の計測対象。1分ステレオで WAV 約10MB に対し webm は約1MB）
- タイムストレッチ / ピッチシフト（#25）。Rubber Band Library 3.3.0 の WASM ビルドを Worker でオフラインに掛け、**ピッチを保ったままテンポだけ**（またはその逆）変える。Web Audio の `playbackRate` は両者が連動するので、素の API では不可能な操作——**ここが「再生機」と「DAW」の分かれ目**。掛け直しは常に読み込んだままの音（`rawBuf`）からで、重ねがけしない。トリムとフェードは尺に比例して伸縮し、設定は保存・復元にも載る
- MP3（CBR 192kbps）書き出し（**このリポジトリ最初の WASM**。LAME 3.100 の WASM ビルドを Worker で回す。オフラインレンダーの結果をエンコードするので webm と違い実時間はかからない。3秒ミックスで WAV 0.5MB → MP3 0.07MB）
- MIDI（`.mid`）の取り込み（#46）。SMF を自前で解析し（`src/lib/midi.ts`・依存ゼロ）、内蔵シンセ（`OscillatorNode` + ADSR）でオフラインレンダーして普通のオーディオトラックにする。**チャンネルごとに1本のトラック**になり、以降はトリム・フェード・EQ/コンプ・バス・書き出し・保存が全部そのまま効く。テンポチェンジ・running status・velocity 0 の note off に対応。**チャンネル10（ドラム）は #54 のドラム音源で鳴らす**（GM のノート番号を キック / スネア / ハイハット / オープンハット に対応づけ、ベロシティも効く。タム・シンバル類は対応する音色が無いので鳴らさず、本数をログに出す）
- ピアノロールでの打ち込み（#55）。2オクターブ × 16分音符の格子にノートを置くと、読み込んだ MIDI と**同じ内蔵シンセ**でレンダーして普通のオーディオトラックにする。長さ（1/2/4/8ステップ）と音色（ピアノ / オルガン / ベース / リード）を選んで置く。**ドラムの格子と違い小節は繰り返さず横に伸びる**（メロディは小節ごとに中身が変わるため）。刻みと BPM の範囲は `src/lib/grid.ts` でドラムと共通
- アプリ内で作るドラムループ（#54）。16ステップ × 4音色の格子を内蔵ドラム音源（正弦波・ノイズ・フィルタの合成。**サンプルは同梱しない**ので増えるバイト数はゼロ）でレンダーし、普通のオーディオトラックにする。プリセット（四つ打ち / 8ビート / シャッフル / クリア）、BPM 40〜240、1〜4小節。**読み込むファイルが1つも無くても曲を始められる**
- プロジェクトの1ファイル書き出し / 読み込み（#81）。`.prism` は無圧縮 ZIP で、中身は `project.json`（端末内保存と同じメタ）と各トラックの元ファイル。他のツールでも開ける。ブラウザのデータが消えても戻せる唯一の道で、別の端末へ持ち出せる。サーバーには送らない。読み込むと今のトラックは置き換わる（確認あり）。版が新しい・壊れている・音声が欠けている、はそれぞれ理由を出す
- プロジェクトの保存・復元（設定は `localStorage`、音声は読み込んだ元ファイルのまま `IndexedDB`。どちらも端末内で完結し、サーバーには何も送らない）
- **自動保存と自動復元（#80）。編集するたびに端末内へ保存し、リロードするとそのまま前回の続きから開く。** 保存を押し忘れて失うことがない。書き込みは編集が止まってから1回にまとめ、音声（`IndexedDB`）は増減したときだけ・設定（`localStorage`・数KB）はそのつど書く。**トラックを全部消しても保存データは消さない**ので、誤って消しても「前回を復元」で戻せる（意図して消すときは「保存データを消す」か「新規プロジェクト」）。共用の端末などで痕跡を残したくないときは Deck の「自動保存」で切れる

## 計測（2026-08-26 / 44.1kHz ステレオ）

画面下段に出る値。**この数字を出すことがこのツールの主目的**なので、UI を作り替えても同等の情報は残す。

| 項目 | v0（単一 HTML） | React 移行後 |
| --- | --- | --- |
| sampleRate | 44,100 Hz | 44,100 Hz |
| 出力レイテンシ | 32.0 ms | 10.0 ms |
| デコード | 2ファイルで 18 ms | 2ファイルで 9 ms |
| PCM メモリ | 2トラック4秒で 1.3 MB | 2トラック5秒で 1.7 MB |
| オフラインレンダー | 4秒を **12 ms＝約323倍速** | 3秒を **10 ms＝約309倍速** |
| MP3 エンコード（WASM / LAME） | — | 3秒を **81 ms＝約37倍速**（0.07MB / WAV 0.5MB の約1/7） |
| タイムストレッチ（WASM / Rubber Band） | — | 30秒を **2,066 ms＝約15倍速**（0.5倍速。下記） |

レイテンシとデコード時間は測った環境（ヘッドレス Chromium vs Artifact ビューア）が違うので直接は比べられないが、**オフラインレンダーの倍率は移行前後で変わっていない**。ここが確認したかった点で、React を挟んでも書き出し速度には効かない——オーディオグラフを React の再描画サイクルの外に置いてあるため。

**ミックスダウンは実時間の数百倍で回る**ので、書き出し速度はブラウザだからという理由ではネックにならない。

エフェクトの追い計測（2026-08-26 / ヘッドレス Chromium / 30秒ステレオ1トラック）: オフラインレンダーは素で **50 ms＝約600倍速**、EQ 3バンド＋コンプを挿すと **265 ms＝約113倍速**。挿入で約5倍かかるが、それでも実時間の100倍以上で回るので、**エフェクトを足しても書き出し速度は問題にならない**。

MP3 書き出しの計測（2026-08-26 / ヘッドレス Chromium / 3秒ステレオ2トラック）: レンダー **10 ms** + WASM（LAME・シングルスレッド）エンコード **81 ms＝約37倍速**。「エンコードを足しても書き出しは数百倍速のままか」（[#20](https://github.com/Naturalclar/prism-river/issues/20)）への答えは **No で、エンコードが支配的になり数十倍速に落ちる**——ただし実時間の30倍超なので、書き出し待ちが問題になる尺ではない（5分の曲でも10秒以内の見込み）。WASM 部分は Worker チャンク（約180KB）に隔離され、メインバンドルには乗らない。

### タイムストレッチの実測（2026-09-05 / ヘッドレス Chromium / 44.1kHz ステレオ1トラック）

[#25](https://github.com/Naturalclar/prism-river/issues/25)。Rubber Band 3.3.0 の WASM ビルド（`rubberband-wasm`）を Worker でオフラインに掛けたときの処理時間。

| 素材の長さ | テンポ 0.5x（尺は2倍） | テンポ 0.75x |
| --- | --- | --- |
| 10秒 | 694 ms（約14倍速） | 501 ms（約20倍速） |
| 30秒 | 2,066 ms（約15倍速） | 1,455 ms（約21倍速） |
| 60秒 | 4,456 ms（約13倍速） | 2,737 ms（約22倍速） |

- **素材の長さにほぼ比例**する（倍率が長さによらず一定）。伸ばす量が大きいほど遅い——出力サンプル数がそのまま仕事量になるため。
- 実時間の10〜20倍速なので、**5分の曲で 20〜30秒**の見込み。書き出し（数百倍速）と違い「待つ処理」で、掛け直すたびに走る。UI はスライダーを `change`（離したとき）で確定させ、計算中はパネルを止める。
- WASM は **265KB（gzip 117KB）** で、Worker が要求したときだけ取りに行く別アセット。ストレッチを使わなければメインバンドル（288KB）には乗らない。
- ピッチだけ動かす場合も尺は変わらないが、処理量は同じ（テンポ 1.0x でも WASM は回る）。

**ライセンス**: Rubber Band Library は **GPL v2 or later**（本家 README の「either version 2 of the License, or (at your option) any later version」）なので、GPL-3.0 のこのリポジトリに取り込める。[#19](https://github.com/Naturalclar/prism-river/issues/19) で GPL-3.0 を選んだのはまさにこの選択肢を残すためで、その判断がここで効いた。商用の別ライセンスを買えば proprietary にも組み込めるが、この台には関係しない。

### 音源分離を ONNX Runtime Web で回せるか（2026-09-05 / ヘッドレス Chromium）

[#27](https://github.com/Naturalclar/prism-river/issues/27) の「サーバー無しでどこまでいけるか」。**分離機能は入れていない。** 入れなかった理由と、代わりに測った数字を残す。

**学習済みモデルは持ち込まない方針**（このリポジトリの制約「外部 API を呼ばない」を守る）で決めたので、Demucs / MDX-Net 等の重みは**使っていない**。代わりに、実物と同じ形（stride 2 で5段畳んで同じだけ戻す U-Net、入力は [1, 2, 512, T] の振幅スペクトログラム）のモデルを**乱数の重みで組んで**測った。生成器は `scripts/separate/onnx.mjs`（protobuf を直に書く依存ゼロの ONNX ライター）で、計測は `pnpm measure:separate`。

**測れたこと / 測れないこと**: 分離の**精度は測っていない**（重みが乱数なので当然）。測ったのは**モデルサイズと尺に対する推論コストとメモリ**——「実用尺を実用時間で回せるのか」「どこで頭打ちになるのか」という、機能を入れる前に知りたかった側。

#### 段1: 積むだけでいくら要るか

| | |
| --- | --- |
| ONNX Runtime Web の WASM | **13.3 MB**（`ort-wasm-simd-threaded.wasm`） |
| 同 JS | 0.35 MB（`ort.min.js`） |
| セッション生成 | **0.6〜1.3 秒**（モデル 3MB でも 108MB でもほぼ変わらない） |

モデルを別にして**14MB 近い実行環境**が要る。この台の現在のバンドルは 288KB なので、**アプリが50倍になる**。セッション生成がモデルサイズにほとんど比例しないのは、重みの読み込みより WASM の初期化が支配的なため。

#### 段3: 尺とモデルサイズに対する推論コスト

44.1kHz / hop 1024（1秒＝約43フレーム）。「実時間比」は 1.0 で実時間、大きいほど速い。

| モデル | 10秒 | 30秒 | 60秒 | 3分 | 5分 |
| --- | --- | --- | --- | --- | --- |
| 3.0 MB | 77 ms (130x) | 220 ms (136x) | 486 ms (123x) | 1,391 ms (129x) | 1,729 ms (173x) |
| 12.0 MB | 127 ms (79x) | 323 ms (93x) | 617 ms (97x) | 1,852 ms (97x) | 4,708 ms (64x) |
| 47.8 MB | 351 ms (28x) | 1,051 ms (29x) | 2,067 ms (29x) | 6,809 ms (26x) | 12,071 ms (25x) |
| 107.6 MB | 707 ms (14x) | 2,175 ms (14x) | 4,358 ms (14x) | 13,529 ms (13x) | 23,940 ms (13x) |

- **尺にはきれいに比例する。** 倍率が尺によらずほぼ一定なので、5分の曲は10秒の30倍の時間で終わる。
- **モデルサイズに反比例する。** 実物と同規模（Demucs / MDX-Net は 50〜300MB 級）の 107.6MB で**実時間の約13倍**、つまり**5分の曲に24秒**。待てない数字ではない。
- 途中で止まらない。**5分の曲を一括で流し切れる**。

#### どこで破綻するか — wasm32 の 4GB が先に効く

[#21](https://github.com/Naturalclar/prism-river/issues/21) と同じ問いを分離側でも見た。**タブのメモリ上限より先に、WASM の 4GB が来る。**

| モデル | 10分 | 15分 | 20分 |
| --- | --- | --- | --- |
| 3.0 MB | 2,178 ms | 5,549 ms | 6,652 ms |
| 12.0 MB | 5,969 ms | 12,087 ms | 14,718 ms |
| 107.6 MB | **`OrtRun()` が `std::bad_alloc`** | — | — |

107.6MB のモデルは 5分（RSS 4.5GB）まで通り、**10分で落ちる**。落ち方は WASM 側の `std::bad_alloc` で、タブのクラッシュではない。ピークを作るのは重みではなく**中間の活性**（幅96・深さ5 の1段目だけで [1, 96, 256, 25824] ＝ 2.5GB）なので、**尺を分割して流せば回避できる**——実装するなら数十秒ずつのチャンク処理が前提になる。

#### スレッド（SharedArrayBuffer）が効く — そして今なら付けられる

同じ 26.9MB のモデル・同じ尺で、`COOP`/`COEP` の有無だけを変えた比較:

| | 30秒 | 60秒 |
| --- | --- | --- |
| スレッド 2（COOP/COEP あり） | 583 ms (51x) | 1,270 ms (47x) |
| スレッド 1（ヘッダなし＝素の GitHub Pages） | 1,134 ms (26x) | 2,082 ms (29x) |

**約2倍違う。** #27 は「SharedArrayBuffer が要る構成なら COOP/COEP が必要で GitHub Pages 単体では付けられない」と書いていて、それは今も正しい。ただし [#62](https://github.com/Naturalclar/prism-river/issues/62) 以降このサイトは **Cloudflare Worker 経由**で配っているので、**Worker 側でヘッダを足せる**。Issue が前提にしていた制約は、デプロイ構成が変わったことで外せる。

#### 結論と、入れなかった理由

- **速度は問題にならない。** 実物と同規模のモデルでも実時間の10倍以上で回り、5分の曲が30秒弱。
- **要るのは覚悟のいるダウンロード。** 実行環境 14MB ＋ モデル 50〜300MB。「`index.html` を開けば動く」という現在の性格とは明らかに釣り合わない。
- **段2（実際に分離できるか）は測っていない。** 学習済みの重みを外から取らないと測れず、それはこのリポジトリの制約に触れる。**ここが未達の唯一の点**で、やるなら「モデルをどこから配るか」を先に決める必要がある（同梱するのか、使うときだけ取りに行くのか、ライセンスは通るのか）。

計測は `pnpm measure:separate` で再現できる（`MEASURE_WIDTHS` / `MEASURE_SECONDS` / `MEASURE_COI` で組み合わせを上書き）。**アプリ本体に ONNX Runtime は入れていない**——使えるモデルが無いまま 14MB を配る意味が無いので、`onnxruntime-web` は計測用の devDependency に留めてある。

### MIDI レンダーの実測（2026-09-01 / ヘッドレス Chromium）

内蔵シンセ（ノートごとに `OscillatorNode` + ADSR）でのオフラインレンダー（[#46](https://github.com/Naturalclar/prism-river/issues/46)）。

| ノート数 × チャンネル | 曲の長さ | レンダー |
| --- | --- | --- |
| 100音 × 1ch | 12.9 s | 198 ms＝約65倍速 |
| 1,000音 × 4ch | 31.7 s | 4,288 ms＝約7倍速 |
| 5,000音 × 8ch | 78.6 s | 59,377 ms＝約1倍速 |

**倍率はノート数とチャンネル数の両方で落ちる。** チャンネルごとに別々の `OfflineAudioContext` を回すので、レンダー総量は「曲の長さ × チャンネル数」に比例し、そこにノート数ぶんのノード生成コストが乗る。実用域（1,000音・4ch 程度の曲）なら4秒前後で終わるが、**密な曲では実時間に近づく**。ここが問題になったら、Web Audio のノードを積むのをやめて Float32 に直接波形を書く（自前シンセ）方が速い——ただし段1 では「標準ノードだけで鳴らす」ことを優先した。

### 長尺・複数トラックの実測（2026-08-26 / ヘッドレス Chromium / メモリ 15GB・4コア）

[#21](https://github.com/Naturalclar/prism-river/issues/21) の「どこで破綻するか」。減衰トーンの WAV を読ませて計測した（`pnpm measure:long` で再現できる）。

| 尺 × 本数 | 総再生分 | デコード | PCM メモリ | ブラウザ RSS | オフラインレンダー |
| --- | --- | --- | --- | --- | --- |
| 5分 × 1 | 5分 | 2,566 ms | 101 MB | 1,175 MB | 627 ms＝約478倍速 |
| 5分 × 2 | 10分 | 4,468 ms | 202 MB | 1,267 MB | 810 ms＝約370倍速 |
| 5分 × 4 | 20分 | 4,875 ms | 404 MB | 1,564 MB | 1,613 ms＝約186倍速 |
| 5分 × 8 | 40分 | 9,821 ms | 808 MB | 2,043 MB | 1,999 ms＝約150倍速 |
| 10分 × 1 | 10分 | 4,354 ms | 202 MB | 1,398 MB | 1,750 ms＝約343倍速 |
| 10分 × 2 | 20分 | 6,292 ms | 404 MB | 1,629 MB | 1,569 ms＝約382倍速 |
| 10分 × 4 | 40分 | 11,059 ms | 808 MB | 2,079 MB | 2,288 ms＝約262倍速 |
| 10分 × 8 | 80分 | 17,608 ms | 1,615 MB | 2,910 MB | 3,735 ms＝約161倍速 |
| 10分 × 16 | 160分 | 40,294 ms | 3,230 MB | 4,369 MB | 8,182 ms＝約73倍速 |
| 10分 × 24 | 240分 | 48,181 ms | 4,845 MB | 5,998 MB | 10,512 ms＝約57倍速 |
| 10分 × 40 | 400分 | 83,598 ms | 8,075 MB | 9,267 MB | 19,567 ms＝約31倍速 |
| 10分 × 56 | 560分 | 89,169 ms | 11,305 MB | 12,441 MB | 30,561 ms＝約20倍速 |

分かったこと:

- **この環境では破綻しなかった。** 10分 × 56本（音声 9時間20分ぶん・PCM 11.3GB・ブラウザ RSS 12.4GB）まで、読み込みも再生も書き出しも通った。**破綻点はアプリ側の実装ではなく端末の物理メモリで決まる**——PCM は AudioBuffer としてブラウザのネイティブ側に載るので、wasm32 の 4GB 上限も JS ヒープ上限も効かない。搭載 16GB の実機なら 10分 × 50本前後が上限の目安。
- **PCM メモリは式どおり線形。** 実測は `長さ(秒) × 44,100 × 2ch × 4 bytes` にぴったり乗る（10分1本で 202MB）。RSS はこれに約 600MB（ブラウザ本体）＋ 1〜2割の作業領域が乗った値。
- **効いてくるのはメモリより先にデコード時間。** 10分 × 40本で 84秒かかる。1本ずつ順に `decodeAudioData` する作りなので、読み込み中はその秒数だけ待たされる（進捗はログに出る）。並列化すればここは縮むが、PCM のピークメモリが跳ねるトレードオフになる。
- **オフラインレンダーの倍率はトラック数とともに落ちる**（1本 478倍速 → 56本 20倍速）。それでも実時間の20倍以上なので、**10分の曲を56本重ねても書き出しは30秒で終わる**。書き出し速度が実用の壁になることはこの範囲では無い。

### ドラムのレンダー実測（2026-09-01 / ヘッドレス Chromium / 120BPM）

1小節（2.00s・8発）を **9 ms**、2小節（4.00s・16発）を **16 ms**、4小節（8.00s・32発）を **42 ms**。実時間の**約200倍速**で、格子を押すたびに作り直しても待ちにならない。合成なので**リポジトリに増える音声データは 0 バイト**。

## 分かっている制約

- **PCM はデコード後 Float32 で保持する。** `長さ(秒) × sampleRate × ch × 4 bytes` なので、**10分ステレオ1本で約202MB**（5分で約101MB）。実測もこの式どおりで、上の長尺計測を参照。破綻点は端末の物理メモリで決まる。
- **`decodeAudioData` の対応形式はブラウザ依存。** 読めない形式・対応外の拡張子は、ファイル名を挙げてその場で伝える作りにしてある。実測した対応表（[#22](https://github.com/Naturalclar/prism-river/issues/22)）:

  | 形式 | Chromium（ヘッドレス・2026-08-26 実測） | Safari (macOS / iOS) | Firefox |
  | --- | --- | --- | --- |
  | wav | ✔ | 未計測 | 未計測 |
  | mp3 | ✔ | 未計測 | 未計測 |
  | ogg (Vorbis) | ✔ | 未計測 | 未計測 |
  | webm (Opus) | ✔（自前の webm 書き出しを読み戻して確認） | 未計測 | 未計測 |
  | m4a (AAC) | 未計測 | 未計測 | 未計測 |
  | flac | 未計測 | 未計測 | 未計測 |

  Chromium 列は E2E（テスト時にその場生成した音源: WAV は自前エンコーダ、MP3/Ogg は wasm-media-encoders、webm は自アプリの書き出し）で毎 CI 検証される。m4a / flac は権利フリーの生成手段が CI に無いため、実機と手持ち音源で埋める。Safari / Firefox 列も実機待ち（モバイル実機の検証は [#23](https://github.com/Naturalclar/prism-river/issues/23)）。
- **動画からの音声取り込みはブラウザ×コンテナ依存。** `decodeAudioData` が動画コンテナの音声をデコードできるかで決まる:

  | コンテナ | ヘッドレス Chromium（CI 実測） | Chrome / Safari / Firefox 実機 |
  | --- | --- | --- |
  | webm（VP8/VP9 + Opus） | ○（e2e で毎回検証） | 未計測（#22 と合わせて確認） |
  | mp4 / mov（H.264 + AAC） | 計測不能※ | 未計測（#22 と合わせて確認） |

  ※ Playwright の Chromium にはプロプライエタリコーデック（H.264 / AAC）が入っておらず、ここで失敗しても実機 Chrome の結果を代表しない。取り出せないときは「◯◯ から音声を取り出せませんでした（このブラウザはこの動画コンテナの音声デコードに対応していません）」と下段のログに出る。実機で読めないコンテナが多いと分かった場合の WebCodecs / デマルチプレクサ導入は #31 の段2として別 Issue に切り出す。
- **Web MIDI API はブラウザ依存。** MIDI キーボード録音（#56）は Chrome / Edge / Firefox が対応、Safari は非対応。非対応ブラウザではその旨をログに出す。実機のキーボード×ブラウザの組み合わせは未計測で、#22 / #23 の実機確認と合わせて埋める（CI はフェイクの `requestMIDIAccess` で受信〜トラック化〜復元まで検証している）。
- claude.ai の Artifact ビューアで開いた場合のみ、`.wav` の保存がビューア側の拡張子許可リストに阻まれる（ブラウザの制限ではない）。このリポジトリから自前でホストする分には関係しない。

## これから

優先度順。検証テーマに効く順で入れ替えてよい。

2. **MIDI のリアルタイム発音** — #56 段1の録音は「無音で弾いて後から確認する」形。今の内蔵シンセはオフラインレンダー専用なので、弾いている音をその場で鳴らすにはリアルタイム発音の仕組みが別に要る。実用上はこちらが本命

### 作りの前提

**オーディオの状態は React の外にある。** `src/audio/engine.ts` の `Engine` が AudioContext・トラック・トランスポートを全部持ち、React は `useSyncExternalStore` でその**スナップショット**を読むだけ。プレイヘッド、時計、レベルメーターのように毎フレーム動くものは `engine.onFrame()` を購読して DOM を直に書き換える——ここに仮想 DOM を挟むと、再生中のトラック操作でオーディオのタイミングにノイズが乗る。

クリップの横ドラッグも同じ理由で、動かしている間は `style.left` を直接書き、指を離したときだけ `commitOffset()` で React と再生グラフを組み直す。

**`Engine` の変更は2種類ある。** 音に効く変更（トラックの増減・音量・パン・ソロ/ミュート・移動・トリム・フェード・エフェクト・バス）は `touched()` で締める。表示だけの変更（選択・ズーム・FX パネルの開閉・トランスポート）は `emit()` のまま。`touched()` は React へ流すのに加えて**書き出し済みのレンダー結果を捨てる**ので、オーディオの機能を足すときはその setter がどちらで終わるかを見ること——`emit()` で済ませると「レンダーを試聴」が編集前のミックスを鳴らす（[#49](https://github.com/Naturalclar/prism-river/issues/49)）。**自動保存（[#80](https://github.com/Naturalclar/prism-river/issues/80)）もこの区別に乗っている**（`onTouched()` を購読する）ので、`emit()` で済ませた変更は保存もされない——「音に効くなら `touched()`」を守る理由がもう1つ増えた形。
